A

쿠버네티스는 왜 도커 위에 또 필요한가

docker run으로 앱 하나를 띄우는 일은 쉽다. 문제는 그 뒤의 운영이다. 도커는 컨테이너를 만드는 도구일 뿐, 컨테이너가 계속 살아있게 하는 도구가 아니다.

상황 도커만 쓸 때 (사람이 직접) 쿠버네티스 (자동)
컨테이너가 죽음 알아채고 docker restart 감지 후 자동 재시작 (자가 치유)
트래픽이 늘어남 서버에 들어가 컨테이너 수를 늘림 replicas: 5 한 줄로 스케일
서버가 여러 대 어느 서버에 띄울지, 포트 겹침을 직접 관리 남은 자원을 보고 알아서 배치
버전 교체 끄고 새로 띄움 → 서비스 중단 하나씩 교체하는 무중단 업데이트
컨테이너 IP가 바뀜 접속 설정이 전부 틀어짐 서비스라는 고정 주소로 해결

그래서 공식 정의는 이렇다: 컨테이너화된 워크로드와 서비스를 관리하는, 선언적 구성과 자동화를 지원하는 확장 가능한 오픈소스 플랫폼.

앱이 2~3개면 없어도 된다. 서비스가 여러 개로 나뉘고 서버가 여러 대가 되는 순간, 관제실이 필요해진다. 쿠버네티스가 그 관제실이다.

B

선언형 vs 명령형 — 말하는 방식부터 다르다

도커에서 하던 방식이 명령형이다. 절차(how)를 한 줄씩 직접 명령한다.

중간에 한 단계를 빠뜨리면 실패하고, 현재 상태는 사람 머릿속에만 있다. 같은 명령을 두 번 치면 오류가 난다.

쿠버네티스의 방식이 선언형이다. 절차가 아니라 최종 상태(what) 를 YAML 파일로 적고 한 번만 적용한다.

이 방식이 강력한 이유는 세 가지다.

  1. 자가 치유: 상태 선언이 항상 유효해, 죽으면 시스템이 알아서 다시 맞춘다.
  2. 멱등성: 같은 YAML을 100번 apply해도 결과가 같다. 스크립트 실수로 상태가 꼬이지 않는다.
  3. Git 관리: 상태가 파일이라 변경 이력을 남기고 되돌릴 수 있다. 이 문화를 GitOps라 부른다.
C

컨트롤 루프 — 자가 치유의 정체

선언만으로는 아무 일도 일어나지 않는다. 누군가 그 선언과 현실을 계속 비교해야 한다. 그 반복이 컨트롤 루프다 (공식 문서 용어. "조정 루프"로 부르기도 한다).

  • 컨트롤러는 컨테이너를 직접 띄우지 않는다. 생성 요청을 API 서버에 보낼 뿐이다.
  • 배치 결정은 스케줄러가, 실제 실행은 kubelet이 담당한다. 흐름이 분업돼 있다.

보일러 온도 조절기와 같은 구조다. 사람은 "23도"만 설정하고, 조절기가 현재 온도를 재서 알아서 켜고 끈다. 매번 "지금 불을 켜라"고 명령하지 않는다. 이 끝없는 관찰-비교-보정 덕분에 파드 하나가 죽어도, 서버 하나가 통째로 죽어도 복구 명령 없이 돌아온다.

D

노드에서 파드가 뜨기까지 — 8단계

읽는 법: ③에서 created 응답이 먼저 돌아오고, ④~⑧은 그 뒤에 자율로 진행된다. 즉 kubectl apply가 끝나도 파드는 아직 안 떴다. API 서버가 "접수"했을 뿐이다. 배치와 실행은 스케줄러와 kubelet이 각자 API 서버를 보며 진행한다.

실습에서 상태가 오래 멈추면 이 지점부터 확인한다: Pending이면 ④(스케줄러가 노드를 못 찾음), ContainerCreating이면 ⑦(이미지 다운로드 중). kubectl get pods -w로 ④~⑧ 과정을 실시간 관찰할 수 있다.

E

클러스터 아키텍처 전체도 — archify 인터랙티브

읽는 법: 위쪽이 컨트롤 플레인(cap-master), 아래 두 박스가 워커 노드(cap-node1, cap-node2) 다. iframe 안을 한 번 클릭한 뒤에는 노드 클릭 → 역할 카드, R(경로 추적), L(렌즈), T(테마) 키가 그대로 작동한다. 12개 관계 중 핵심은 하나다 — 모든 화살표가 API 서버로 모인다. 어떤 구성요소도 서로 직접 대화하지 않는다.

F

컨트롤 플레인 5종 — 각각 무엇을 책임지나

컨트롤 플레인은 클러스터 전체를 감시하고 결정하는 두뇌 모음이다. 실습에서는 cap-master 한 대에 전부 들어가고, kube-system 네임스페이스의 Static Pod로 뜬다.

컴포넌트 역할 멈추면
kube-apiserver HTTP API 제공. 인증, 검증, etcd에 기록, 변화 통보 — 모든 요청의 유일한 관문 kubectl 전부 실패. 실행 중 파드는 계속 서비스
etcd 일관성과 고가용성을 갖춘 키-값 저장소. 클러스터의 모든 상태를 저장 변경 불가. 백업이 없으면 복구 불가 — 백업 1순위 대상
kube-scheduler 노드에 할당되지 않은 파드에 알맞은 노드를 배치 새 파드가 Pending에 멈춤. 기존 파드는 멀쩡
kube-controller-manager 컨트롤러들을 실행해 상태를 관리 (자가 치유, 스케일) 자동 복구와 스케일 중지
cloud-controller-manager 클라우드 공급자와 클러스터를 통합 (LB, 볼륨). 선택 사항 클라우드 자원 연동만 중지

기억할 것 두 가지. 첫째, API 서버는 아무 결정도 내리지 않는다. 접수, 검증, 기록, 통보만 하고 결정은 스케줄러와 컨트롤러가 한다. 둘째, 관제실이 멈춰도 서비스는 산다. 이미 떠 있는 파드는 각 노드의 kubelet이 돌리고 있어서 계속 서비스한다. 새 배포와 조회와 자동 복구만 멈출 뿐이다.

흐름으로 외우면 이렇다: 컨트롤러가 "무엇을" 결정 → 스케줄러가 "어디에" 결정 → kubelet이 실행. 그리고 이 세 대화창구가 전부 API 서버다.

G

워커 노드 — kubelet과 containerd, kube-proxy

노드는 실제로 컨테이너가 돌아가는 서버 한 대다. 노드마다 세 가지가 상주한다.

kubelet — 현장 반장. 노드에서 파드와 그 안의 컨테이너의 실행을 관리한다. 담당 일은 세 가지다: API 서버에 "내 노드에 배정된 파드"를 계속 물어보고(⑥), containerd에 실행을 지시하고(⑦), 현재 상태를 계속 보고한다(⑧). 파드가 죽으면 다시 띄우는 것도 kubelet이다.

컨테이너 런타임 containerd — 작업자. 컨테이너를 실제로 실행하는 소프트웨어다. 도커의 핵심 엔진과 같은 뿌리다. 예전에 쓰던 "도커 연결 계층(dockershim)"은 v1.24에서 제거됐는데, 이는 도커로 만든 이미지를 못 쓴다는 뜻이 아니다. 이미지 그대로 쓰인다. 중간 연결 계층만 없어진 것이다.

kube-proxy — 안내 데스크. 서비스 구현을 위해 노드의 네트워크 규칙(iptables)을 유지한다. 서비스(ClusterIP)로 들어온 트래픽을 실제 파드로 전달하는 규칙이 kube-proxy가 깔아 둔 것이다. 선택 사항이며, 서비스 네트워킹을 다른 구현이 담당할 수도 있다.

kubelet의 존재가 "관제실이 죽어도 서비스는 산다"의 근거다. 관제실이 죽어도 반장은 현장에 남아 있다.

H

파드 — 왜 컨테이너를 그대로 쓰지 않았나

파드는 쿠버네티스가 생성하고 관리하는 최소 배포 단위다. 컨테이너 1개 이상과 그 실행 명세를 담는다.

특성 내용
구성 컨테이너 1개 이상 + 실행 명세
네트워크 파드마다 IP 하나. 파드 안 컨테이너는 localhost로 통신
스토리지 파드 안 컨테이너가 스토리지 볼륨을 공유
배치 파드 안 컨테이너는 항상 같은 노드에 함께 배치, 스케줄
수명 일시적. 장애 시 컨트롤러가 대체 파드를 생성

컨테이너를 곧바로 배포하지 않고 파드로 감싼 이유는, 배치 단위를 통일하기 위해서다. IP를 누가 받을지, 포트와 볼륨을 어디까지 공유할지가 파드에서 한 번에 정해진다. 같은 노드의 파드들끼리도 IP가 겹치지 않는다.

한번 죽은 파드는 완전히 새로 태어난다 — 새 이름, 새 IP. 이 특성이 3일차에 나올 레이블과 셀렉터, 서비스를 필요하게 만든다. 실무에서는 컨테이너 1개짜리 파드가 표준이고, 로그 수집기 같은 보조 프로세스만 함께 담는다(사이드카).

파드가 담는 두 정보를 구분하자: spec은 내가 선언한 원하는 상태이고 사람이 쓴다. status는 현재 상태이고 쿠버네티스가 채운다. 사람은 status를 쓰지 않는다.

I

애드온 — kube-system 네임스페이스

애드온은 클러스터의 기능을 확장하는 추가 컴포넌트다. 대부분 데몬셋(DaemonSet)으로 배포되며, kube-system 네임스페이스에 뜬다.

  • CoreDNS: 클러스터 내부 DNS를 제공해 서비스 디스커버리를 지원한다. 파드는 서비스 이름을 DNS로 조회해 ClusterIP를 얻는다. IP를 직접 적지 않기 때문에 서비스를 찾을 수 있다.
  • kube-proxy: 공식 문서 분류상 노드 컴포넌트다. 다만 kubeadm init에서는 CoreDNS와 함께 애드온 단계로 설치된다. 설치 방법과 컴포넌트 분류가 다르다는 뜻이지, 역할이 애드온이라는 뜻은 아니다.
  • Calico: CNI 플러그인이다. 파드마다 Pod 대역 IP를 나눠 주고, 노드 간 파드 통신을 VXLAN 터널로 연결한다. 이 실습에서 선택한 CNI다.

설치가 끝나면 kubectl get pods -n kube-system으로 오늘 배운 이름들(API 서버, etcd, 스케줄러, 컨트롤러 매니저, CoreDNS, kube-proxy)을 직접 확인한다. 컨트롤 플레인 5종 + CoreDNS는 모두 Static Pod로 뜬다. kubelet이 API 서버 없이 /etc/kubernetes/manifests/의 매니페스트를 직접 읽어 기동하는 예외 경로다. 닭과 달걀 문제(API 서버도 파드인데 파드를 띄우려면 API 서버가 필요)를 푸는 방법이다.
