A

1교시 · Pod = 함께 살고 함께 죽는 컨테이너 묶음

도커에서는 컨테이너가 최소 단위였다. 그런데 nginx와 로그 수집기처럼 같은 파일을 주고받으며 항상 붙어 다녀야 하는 둘은 어떻게 다룰까?

문제부터 보기 — 컨테이너 두 개를 따로 띄우고 네트워크로 잇는 것이 순진한 해법이다. 하지만 서로 다른 노드에 배치될 수 있고, 한쪽만 교체되면 짝을 다시 찾아야 하며, 로컬 로그 파일을 공유하려면 배치와 저장소를 별도로 맞춰야 한다.

해결 — 항상 함께 배치되고 함께 사라지며 네트워크·볼륨을 공유하는 묶음을 만든다. 이것이 Pod다.

이게 틀어지면 — 함께 다닐 필요가 없는 것(앱과 DB)을 한 Pod에 넣으면 따로 늘릴 수 없고 Pod 교체 때 함께 영향을 받는다. 컨테이너 하나만 재시작하는 것은 가능하지만, 독립된 서비스처럼 배포하는 단위는 아니다. 5장에서 손대기 어려워진다.

한 Pod 안에서 공유하는 것과 공유하지 않는 것이 절반이다:

공유하는 것 공유하지 않는 것
네트워크 — Pod IP 하나, 서로 localhost로 통신 파일 시스템 — 각자 자기 이미지의 루트를 가짐
볼륨 — 같은 볼륨을 각자 마운트해 파일 교환 프로세스 공간 — 기본적으로 분리
생명주기 — Pod 단위 배치·삭제, 컨테이너별 재시작 가능 이미지·리소스 한도 — 컨테이너별로 지정

Pod는 "같은 방을 쓰는 룸메이트"다. 방(네트워크·볼륨)은 함께 쓰지만 옷장(파일 시스템)은 각자다. 이사도 같이 간다.

Pod와 도커 컨테이너의 실제 관계 — netns와 mountns

왜 필요한가 — Pod는 더 큰 도커 컨테이너가 아니라 API 객체다. 실제 격리는 리눅스 네임스페이스와 런타임이 구현하므로 도커로 빌드한 이미지를 실행해도 Docker Engine이 필수는 아니다.

어떻게 동작하는가 — 일반적인 리눅스 Pod 하나에는 공유 네트워크 네임스페이스(netns) 하나가 있고, 컨테이너마다 별도 마운트 네임스페이스(mountns)가 있다. netns는 네트워크 인터페이스·IP·포트 공간을 정하고, mountns는 어떤 경로에 어떤 파일시스템이 보이는지 정한다. 따라서 api의 /app과 log-agent의 /app은 같은 이름이어도 다른 이미지의 디렉터리다.

공유 볼륨은 두 mountns에 같은 저장소를 각각 연결해서 만든다. 앱은 /var/log/app에, 수집기는 /logs에 마운트해도 같은 파일을 본다. 경로 문자열이 같아서 공유되는 것이 아니라 같은 volumes 항목을 참조하기 때문에 공유된다. 프로세스 네임스페이스는 기본적으로 분리되므로 한쪽에서 다른 쪽 프로세스를 바로 보는 구조도 아니다.

도커에서 익숙한 대상 Pod에서 대응되는 대상 확인할 경계
이미지 한 개로 띄운 컨테이너 Pod 안의 개별 컨테이너 이미지·루트 파일시스템은 각각 유지된다
컨테이너별 네트워크 Pod의 공유 netns localhost와 포트 공간을 함께 쓴다
bind mount·volume volumes와 각 컨테이너의 volumeMounts 양쪽 모두 마운트해야 같은 파일이 보인다
Docker Engine에 실행 요청 kubelet이 CRI 런타임에 실행 요청 Lab02의 런타임 설정이 실제 실행을 맡는다

틀어지면 어떻게 되는가 — 경로 이름만 맞추거나 공유 볼륨을 한쪽에만 마운트하면 수집기는 자기 이미지의 빈 경로를 읽는다. 양쪽 volumeMounts의 볼륨 이름과 경로를 비교한다. 반대로 포트 공간은 공유하므로 두 프로세스가 같은 IP의 5000번 포트를 열면 두 번째는 보통 address already in use로 종료된다.

이 설명은 Lab02의 일반적인 리눅스·컨테이너 런타임 구성을 기준으로 한다. hostNetwork나 가상머신 기반 런타임처럼 격리 방식이 다른 선택지는 오늘 다루지 않는다.

B

1교시 · pause 컨테이너 — 보이지 않는 자리 지키기

YAML에 쓰지 않은 컨테이너가 하나 더 있다. Lab02처럼 일반적인 리눅스 런타임을 쓰면 Pod sandbox를 유지하는 pause 컨테이너가 보인다. 모든 런타임이 반드시 같은 구현을 쓰는 것은 아니다.

문제 — 한 Pod의 컨테이너들이 IP 하나를 함께 써야 하는데, 컨테이너는 각자 뜨고 각자 죽는다. 로그 수집기가 재시작되는 동안에도 Pod IP는 그대로여야 한다.

해결 — 아무 일도 하지 않고 잠만 자는 컨테이너를 가장 먼저 띄워 네트워크·IPC 네임스페이스를 붙잡아 두고, 나머지 컨테이너가 그 자리에 들어온다.

이게 틀어지면 — sandbox가 손상되면 앱 프로세스만 다시 띄워서는 공유 네트워크 환경을 복구할 수 없다. kubelet과 런타임이 sandbox와 연결된 컨테이너들을 재구성해야 하고, 기존 연결도 끊길 수 있다. 일반적인 삭제에서는 앱 컨테이너를 정리한 뒤 sandbox를 정리한다(First In · Last Out).

실행 순서로 보면: 생성 — sandbox 준비 → initContainers를 선언 순서대로 진행 → 일반 앱 컨테이너 시작. 네이티브 사이드카는 initContainers 순서에 포함되고 계속 살아 있으며, 일반 containers에 둔 사이드카와 앱 사이에는 시작 순서 보장이 없다. 삭제 — 앱 종료 → 네이티브 사이드카 종료 → sandbox·네트워크 정리, IP 할당 해제다. 종료 요청 뒤 유예 시간 안에 끝나지 않은 프로세스는 강제 종료된다.

pause는 주차 공간에 먼저 세워 두는 고깔(라바콘)이다. 차(앱 컨테이너)가 들어왔다 나가도 고깔이 있는 동안은 그 자리가 우리 자리다. 고깔을 치우는 순간 자리가 남에게 넘어간다 — 이때 네트워크 플러그인이 IP 할당을 해제하므로, 이후 다른 Pod가 그 주소를 받을 수 있다. 이것이 Pod IP 반환이다.

CRI는 실행 요청 규약이고 pause는 그 실행 환경의 일부다

왜 필요한가 — kubelet이 Docker Engine 전용 명령만 사용하면 런타임을 바꿀 때 kubelet도 바뀌어야 한다. CRI(Container Runtime Interface)는 kubelet과 containerd·CRI-O 같은 런타임 사이의 공통 요청 규약이다. pause는 규약 자체가 아니라 일반적인 런타임이 Pod sandbox를 유지하는 데 쓰는 작은 컨테이너다.

어떻게 동작하는가 — API 서버에 저장된 Pod가 노드에 배정되면 kubelet이 CRI의 RunPodSandbox 요청으로 실행 환경을 준비한다. 런타임은 네트워크 플러그인(CNI)과 연계해 인터페이스와 IP를 마련하고, 그 sandbox에 속할 앱 컨테이너를 CreateContainer·StartContainer 요청으로 만든다. kubelet이 YAML을 pause에 전달하거나 pause가 앱을 실행하는 구조가 아니다. 공식 CRI 설명에서 이 역할 분리를 확인할 수 있다.

틀어지면 어떻게 되는가 — sandbox 생성이나 CNI 설정이 실패하면 이미지에 문제가 없어도 앱은 시작하지 못한다. Events의 FailedCreatePodSandBox는 이 단계의 단서다. 이미지 인증 실패와 구분해야 하며, 이 경우에는 Lab02에서 설정한 런타임 연결과 CNI 상태를 확인해야 한다.

C

1교시 · 무엇을 한 Pod에 넣고, 무엇을 나눌 것인가

기준은 네 가지다. 배치·복제·생명주기를 함께 묶을 필요가 있는지 먼저 판단한다. 보조 이미지를 따로 빌드한다는 이유만으로 반드시 Pod를 나누는 것은 아니다.

질문 뜻
① 같이 살고 같이 죽어야 하나 주 컨테이너가 사라지면 보조도 존재 이유가 없는가
② 같은 수로 늘어나야 하나 주 컨테이너 3개면 보조도 3개가 맞는가
③ 같은 노드에 있어야만 하나 로컬 파일이나 localhost로 주고받는가
④ 독립 서비스로 배포·롤백해야 하나 보조 버전 변경 때 앱 Pod까지 교체해도 되는가
같이 넣는 조합 나눠야 하는 조합
앱 + 로그 수집기 (Lab03의 shop-web) 앱 + DB — 늘리면 데이터가 갈라짐
앱 + 프록시(사이드카) 웹 + API — 트래픽 특성이 달라 따로 늘려야 함
앱 + init(준비 작업) 앱 + Redis — Pod마다 따로 생겨 공유 불가
앱 + 지표 변환기(어댑터) 서로 다른 팀의 서비스 — 배포 권한이 섞임

가장 흔한 실수는 앱과 DB를 한 Pod에 넣는 것이다. 도커 컴포즈는 "내 PC에 한 벌 띄우기"가 목적이고 쿠버네티스는 "여러 대로 늘리기"가 목적이라 전제가 다르다.

고민될 때 판별 질문 두 개: "이걸 3개로 늘리면 다른 것도 3개가 되어야 하나?" → 아니오면 분리. "한쪽만 독립된 복제 수와 배포 일정으로 운영해야 하나?" → 그렇다면 분리. 사이드카 이미지는 앱과 따로 빌드·태그 관리할 수 있지만, Pod 템플릿을 바꿔 배포하면 앱을 포함한 Pod가 교체된다는 차이가 있다.

D

1교시 · Pod는 일회용이다 — phase와 재시작 규칙

Pod는 고쳐 쓰는 물건이 아니라 버리고 새로 만드는 물건이다. 삭제된 Pod는 되살아나지 않고, 컨트롤러가 관리할 때만 대체 Pod를 만든다. UID는 반드시 새 값이다. 이름을 다시 쓸 수는 있고 IP도 재사용될 수 있지만, 이전 Pod와 같은 객체는 아니다.

phase 뜻
Pending 아직 노드 배치 전이거나 이미지 받는 중
Running 노드에 배치되고 모든 컨테이너가 생성됨. 하나 이상 실행 중이거나 시작·재시작 중
Succeeded / Failed 모두 성공 종료 / 모두 종료 후 일부 실패 또는 시스템의 실패 판정
Unknown 노드와 통신할 수 없는 등의 이유로 상태를 파악하지 못함

주의: Running은 "떠 있다"는 뜻이지 "요청을 받을 준비가 됐다"는 뜻이 아니다. 그 구분이 READY 열이며, 준비 상태를 다루는 것이 Probe다.

재시작 규칙(restartPolicy)은 셋이다: Always(기본, 상주 서비스) · OnFailure(Job) · Never(일회성 작업).

Lab02의 기본 설정에서 반복 실패하면 재시작 간격이 10초 → 20초 → 40초로 늘어나 최대 5분이 된다. CrashLoopBackOff가 이 상태다. 원인 이름이 아니라 “반복 실패 뒤 재시도를 기다리는 중”이라는 표시다. 앱 오류·잘못된 시작 명령·메모리 부족처럼 실제 고장이 그 아래에 있을 수 있다. 반대로 10분간 문제없이 실행되면 백오프 타이머가 초기화되므로, RESTARTS 숫자만 보고 현재 장애로 판단하지 마라 — kubectl describe pod의 Last State와 마지막 재시작 시각을 함께 봐야 한다.

같은 Pod의 재시작과 새 Pod의 생성은 다르다

왜 필요한가 — RESTARTS가 늘어도 “삭제한 Pod가 자동 복원된다”는 뜻은 아니다. 컨테이너 재시작은 kubelet, 대체 Pod 생성은 컨트롤러의 일이다.

어떻게 동작하는가 — 종료 프로세스는 restartPolicy에 따라 같은 UID 안에서 재시작한다. 노드가 사라지면 Pod를 그대로 옮기는 대신, 컨트롤러가 새 UID의 Pod를 만들고 스케줄러가 배치한다. 직접 만든 Pod에는 이 복제 수 관리가 없다.

틀어지면 어떻게 되는가 — 잘못된 설정으로 재시작만 반복할 수 있다. Events로 이미지·볼륨 오류, Last State와 이전 로그로 종료 원인을 본다. Pending도 자원 부족으로 단정하지 말고 노드 배정과 대기 이유를 나눠 읽는다.

Pod의 유동성(liquidity)이 자가치유와 롤링 업데이트를 가능하게 한다

왜 필요한가 — 기존 서버의 상태·IP를 살려야 하면 복구가 서버 수리에 매달린다. 이미지와 선언으로 다시 만들 수 있으면 인스턴스를 교체해 복구한다. liquidity는 API 필드가 아니라 Pod를 교체할 수 있는 유동성을 뜻한다.

어떻게 동작하는가 — 자가치유에서는 “API 세 개가 필요하다”는 선언과 실제 수가 어긋나면 컨트롤러가 부족한 Pod를 만든다. 롤링 업데이트에서는 새 이미지의 Pod를 먼저 만들고 준비 상태를 확인한 뒤 기존 Pod를 순차적으로 줄인다. 이전 프로세스의 내부 상태를 옮기는 대신 동일한 역할의 새 프로세스로 바꾼다. 5장 Deployment는 이 교체 속도와 가용 복제 수를 관리한다.

틀어지면 어떻게 되는가 — Pod IP를 다른 앱 설정에 고정하거나 장바구니를 앱 메모리에만 저장하면 새 Pod를 만든 뒤 연결이나 데이터가 깨진다. 3일차 Service는 바뀌는 Pod 앞에 안정적인 접근 주소를 제공한다. emptyDir는 같은 Pod의 컨테이너 재시작 때 남지만 Pod 교체 때 사라진다. 영구 데이터는 외부 저장소로 옮겨야 하며, 오늘 shop-api의 DB_MODE=memory는 실습 편의를 위한 값이라 Pod 교체 때 데이터 보존을 보장하지 않는다.

자가치유는 버그 수정을 대신하지 않는다. 잘못된 이미지나 설정을 선언했다면 컨트롤러는 그 잘못된 상태도 충실히 복제한다. 선언을 고치고 다시 배포해야 복구된다.

E

2교시 · shop-api manifest 해부

2교시는 선언 파일을 줄 단위로 읽는 시간이다. 형태는 1일차와 같지만, 이번엔 앱 진짜 이미지를 띄운다.

주의 — containerPort는 방화벽을 여는 설정이 아니다. 도구가 참조할 포트 정보이며 앱의 listen 설정을 바꾸지 않는다. 다른 Pod에서 쓸 안정적인 접근 주소는 Service에서, ALB를 통한 외부 공개는 7일차에 배운다. 초보자가 가장 많이 오해하는 필드다.

manifest의 각 필드는 누구에게 보내는 지시인가

왜 필요한가 — YAML은 앱이 직접 읽는 실행 파일이 아니다. kubectl이 API 서버에 전달하는 객체 선언이다. metadata는 API 서버·조회 도구·컨트롤러가 객체를 식별하는 정보이고, Pod의 spec은 노드에서 실행할 조건이다. 다만 spec 전체를 kubelet만 읽는 것은 아니다. 스케줄러도 배치 조건을 읽는다.

원문 필드 주로 읽는 주체 이 값이 하는 일
apiVersion: v1 API 서버 사용할 API 스키마와 버전을 정한다
kind: Pod API 서버·kubectl 생성할 객체 종류를 정한다
metadata.name: shop-api API 서버·도구 같은 네임스페이스 안에서 객체를 식별한다
metadata.namespace: shop API 서버·권한 검사 저장·조회·권한 검사의 범위를 정한다
metadata.labels.app / tier 조회 도구·셀렉터를 쓰는 구성요소 shop의 api 역할인 Pod를 찾게 한다
spec.containers kubelet 실행할 컨테이너들의 목록을 정한다
containers[].name: api kubelet·로그 조회 도구 Pod 내부의 컨테이너를 구분한다
containers[].image kubelet → CRI 이미지 서비스 받아서 실행할 이미지 주소를 정한다
ports[].containerPort: 5000 도구·포트 참조를 쓰는 리소스 컨테이너가 사용할 포트를 선언한다
env[].name / value kubelet → CRI 런타임 → 앱 프로세스 환경에 DB_MODE=memory를 넣는다

어떻게 동작하는가 — API 서버가 스키마·권한 검사 후 저장하면 스케줄러가 노드를 정한다. 해당 kubelet이 이미지·네트워크·프로세스를 준비하고 결과를 status로 보고한다. 저장 성공과 실행 성공은 다르다. 공식 객체 설명의 spec은 원하는 상태, status는 관찰 상태다.

틀어지면 어떻게 되는가 — labels의 tier를 잘못 적으면 Pod는 실행되더라도 나중에 Service가 찾지 못한다. image가 잘못되면 객체 생성은 성공한 뒤 이미지 받기 단계에서 실패한다. containerPort를 5000으로 써도 앱이 8080에서 듣는다면 실제 리스닝 포트는 8080이다. 이 필드는 앱을 대신해 소켓을 열어 주지 않는다.

F

2교시 · 떠 있는 Pod를 고쳐도 되는가 — kubectl edit의 한계

Pod는 "고쳐 쓰는 것이 아니라 버리는 단위"라서, 떠 있는 상태에서 바꿀 수 있는 필드가 정해져 있다.

떠 있는 상태에서 바꿀 수 있는 것 바꿀 수 없는 것 (삭제 후 재생성)
image — 이미지 태그 교체 command · args · env · envFrom
labels · annotations volumes · volumeMounts
tolerations 추가(삭제는 불가) 컨테이너 추가·삭제
activeDeadlineSeconds nodeName · nodeSelector · restartPolicy

바꿀 수 없는 필드를 고쳐 apply하면 spec: Forbidden: pod updates may not change fields other than spec.containers[*].image 오류가 난다. Lab03에서 직접 마주친다.

비유: 집을 다 지은 뒤에는 벽지(이미지)는 바꿀 수 있지만 방 구조(볼륨·환경변수)는 바꿀 수 없다. 구조를 바꾸려면 헐고 다시 짓는다(delete → apply).

참고: CPU·메모리 resources의 실행 중 변경은 클러스터 버전과 런타임의 in-place resize 지원 조건에 따라 가능하다. command·env·볼륨 변경까지 허용하는 기능은 아니다. 5장 Deployment는 템플릿 변경으로 새 Pod를 만들어 순차 교체한다. kubectl edit으로 급히 허용 필드를 바꿨다면 선언 파일도 함께 고쳐야 한다.

직접 수정의 결과를 선언 파일에 되돌려 놓는다

왜 필요한가 — 객체만 급히 수정하고 파일을 남겨 두면 다음 apply에서 과거 값으로 돌아갈 수 있다. 현재 상태와 선언이 갈라진 드리프트다.

어떻게 동작하는가 — API 서버는 허용 필드만 수정한다. 직접 Pod의 env·볼륨 변경은 파일 수정 뒤 삭제·재생성이 필요하고, 그 사이 요청을 받을 Pod가 없을 수 있다.

틀어지면 어떻게 되는가 — 거부된 apply는 이전 값을 바꾸지 않는다. 실제 spec과 파일을 비교하고, Deployment를 쓸 때도 원하는 값을 템플릿에 기록해야 한다.

G

2교시 · kind에 맞는 apiVersion 찾기

apiVersion은 kind마다 다르다(Pod=v1, Deployment=apps/v1, Job=batch/v1). 외울 필요 없이 클러스터에 직접 물어본다.

방법 1 — kubectl api-resources (목록에서 찾기): APIVERSION 열을 apiVersion: 줄에 그대로 복사. KIND는 대소문자 구분, NAMESPACED가 false면 -n 옵션이 의미 없음(Node · PersistentVolume). 주의: SHORTNAMES(deploy, sts)는 명령어용일 뿐, manifest의 kind:에는 Deployment를 써야 한다.

방법 2 — kubectl explain (한 개를 확실히): GROUP과 VERSION을 합치면 apps/v1. GROUP이 비어 있으면 core 그룹이라 v1만 쓴다(Pod · Service · ConfigMap · Secret). explain은 필드까지 알려 줘서 YAML을 쓸 때 문서보다 빠르다.

방법 3 — kubectl api-versions (이 클러스터가 아는 그룹 전체): 여기 없는 그룹을 manifest에 적으면 no matches for kind ... 오류가 난다.

자주 쓰는 조합: v1(Pod·Service·ConfigMap·Secret) · apps/v1(Deployment·StatefulSet) · batch/v1(Job·CronJob) · networking.k8s.io/v1(Ingress) · autoscaling/v2(HPA).

이 방법은 CRD에도 그대로 통한다. "CRD를 설치한다 = 클러스터가 아는 kind가 늘어난다"를 6일차에 눈으로 확인하게 된다.

버전 오류와 실행 오류를 구분한다

왜 필요한가 — 지원하지 않는 apiVersion은 객체 해석 단계에서, 잘못된 이미지는 노드 실행 준비 단계에서 실패한다.

어떻게 동작하는가 — api-resources로 그룹·버전을 고르고 explain으로 필드 위치와 타입을 읽는다. core/v1과 apps/v1은 다른 API다.

틀어지면 어떻게 되는가 — Pod에 apps/v1이나 SHORTNAMES를 쓰면 실행 전 거부된다. 오래된 예제도 현재 클러스터의 API 목록으로 확인한다.

2교시 · 이미지 주소 읽는 법

조각 값 뜻
레지스트리 ghcr.io 이미지 보관소 (생략하면 Docker Hub)
소유자/이름 worldvit/skillboost-api 저장소 경로
태그 :v1 버전 (생략하면 latest)

imagePullPolicy 기본값: 태그가 latest이거나 생략이면 Always, 구체적 태그(:v1 등)면 IfNotPresent.

latest는 "최신"이라는 약속이 아니라 그냥 이름이다. 어제의 latest와 오늘의 latest가 다른 이미지일 수 있어 운영에서는 쓰지 않는다. latest를 쓰면 노드마다 다른 버전이 돌고, "어제는 됐는데 오늘 안 되는" 재현 불가 장애가 생긴다. 새 빌드는 반드시 새 태그로 올린다(5장 롤백이 가능한 이유).

태그와 캐시가 만나는 지점

왜 필요한가 — 같은 :v1 태그를 새 이미지로 덮어쓰면 IfNotPresent인 노드는 이미 받은 옛 이미지를 재사용한다. 새 노드는 새 이미지를 받으므로 같은 manifest인데도 동작이 갈라진다. 변경 이력을 추적할 수 있는 태그를 유지해야 하는 이유다.

어떻게 동작하는가 — imagePullPolicy 기본값은 객체를 처음 만들 때 정해진다. 나중에 image를 latest로 바꿨다고 기존 IfNotPresent가 자동으로 Always가 되는 것은 아니다. Always도 무조건 모든 레이어를 다시 다운로드한다는 뜻은 아니다. 레지스트리에서 이미지 식별자를 확인하고 로컬에 같은 내용이 있으면 캐시를 사용할 수 있다. 공식 이미지 문서는 정책과 캐시를 구분한다.

틀어지면 어떻게 되는가 — 레지스트리 주소·태그가 없거나 인증이 실패하면 ErrImagePull 이후 ImagePullBackOff로 재시도를 기다린다. 이때는 앱 코드가 아직 실행되지 않았으므로 앱 로그가 없는 것이 자연스럽다. Events에서 이미지 이름과 인증·네트워크 오류를 먼저 읽는다. 이미지 내용을 완전히 고정하려면 태그보다 digest를 사용하는 방법도 있다.

2교시 · 네임스페이스 — 클러스터 안의 구역

한 클러스터를 여러 팀·여러 용도로 쓰려면 이름 앞에 접두어를 붙이는 것만으로는 부족하다. 권한도, 자원 한도도, 조회 범위도 나눌 수 없다. 네임스페이스는 클러스터 안의 논리적 구역이고, 그 안에서만 이름이 유일하다.

네임스페이스가 나누는 것: 이름(shop/api와 test/api 공존) · 권한(RBAC) · 자원 한도(ResourceQuota) · 조회 범위 · 정리 단위(지우면 안의 것 한꺼번에 삭제).

주의 — 네트워크는 네임스페이스 생성만으로 나뉘지 않는다. 별도 정책이 없다면 shop의 Pod가 test의 Pod에 접속할 수 있다. 통신까지 제한하려면 NetworkPolicy와 이를 집행하는 CNI가 필요하다. "방 칸막이일 뿐 방음벽이 아니다."

운영과 개발을 같은 클러스터의 다른 네임스페이스로만 나누는 것은 위험하다 — 컨트롤 플레인·노드를 공유하므로 개발 쪽 부하가 운영을 흔들 수 있다.

실습에서 쓰는 구역: shop(우리 앱) · kube-system(클러스터 구성요소) · kube-public · kube-node-lease(내부용, 손대지 않음) · default(지정 없으면 여기, 실습 미사용).

생성은 두 가지다. 명령형 kubectl create namespace shop(빠름) vs 선언형 — 00-namespace.yaml을 만들어 apply(Git에 남음, 권장). 두 방법의 차이는 1일차 명령형/선언형 차이 그대로다.

매번 -n shop을 치기 번거로우면 kubectl config set-context --current --namespace=shop으로 기본값을 바꿀 수 있지만, 실습 문서는 -n shop을 계속 쓴다. 기본값은 kubeconfig에 저장되어 같은 파일·컨텍스트를 쓰는 다른 터미널과 새 세션에도 적용되지만, 다른 kubeconfig나 컨텍스트를 쓰면 조회 범위가 달라지고, 명령만 봐서는 어느 구역에 적용되는지 알 수 없으며, 실무에서 이 기본값 때문에 운영 네임스페이스에 실수 적용하는 사고가 자주 일어난다. 기본 컨텍스트를 바꾸지 않은 상태에서 -n shop을 빠뜨리면 default를 보게 되어 "Pod가 없다"고 착각한다 — 2일차 내내 가장 흔한 실수. 전체를 보려면 kubectl get pods -A.

네임스페이스를 언제 쓰지 않는가

왜 필요한가 — 클러스터가 작고 한 팀이 앱 하나를 운영하는데 컨테이너마다 구역을 나누면, 나눌 권한이나 자원 한도는 없고 참조와 명령만 복잡해진다. 사용자 수보다 실제로 분리해야 할 운영 경계가 있는지가 기준이다. 공식 네임스페이스 설명도 소규모 환경에서 필요 없이 구역을 늘릴 이유가 없다고 설명한다.

어떻게 동작하는가 — Pod가 ConfigMap·Secret을 이름으로 참조하면 같은 네임스페이스에서 찾는다. web과 api를 다른 구역에 넣으면 공통 설정을 각 구역에 준비해야 하고, Service의 DNS 주소도 네임스페이스를 고려해야 한다. 단순히 역할을 구분하려면 먼저 app·tier 라벨로 조회하는 편이 낫다.

틀어지면 어떻게 되는가 — 설정은 default에 만들고 Pod는 shop에 만들면 같은 이름의 설정이 있어도 찾지 못한다. Pod를 보려고 다른 구역을 조회하는 실수도 늘어난다. 실습의 shop은 명령 범위와 삭제 경계를 배우기 위한 의도적인 선택이지, 모든 앱에 별도 구역을 강제하는 규칙이 아니다.

오늘 브라우저로 쇼핑몰을 열면 "API 연결 실패"가 뜨는 것이 정상이다. 화면(shop-web)과 API(shop-api)를 이어 줄 Service를 아직 배우지 않았기 때문이다. 3일차에서 연결된다. 다만 Pod가 이미지 받기나 init 단계에서 실패한 것은 이 안내와 별개의 오류다. 오늘은 두 Pod가 실행되고 각 컨테이너의 로그가 보이는지까지 확인한다.

명령어 하는 일 메모
kubectl api-resources 이 클러스터가 아는 리소스(kind) 전체 목록 APIVERSION 열 값이 manifest의 apiVersion이 된다. SHORTNAMES(deploy 등)는 명령어용일 뿐
kubectl explain <kind> 한 kind의 apiVersion과 필드 구조를 보여 줌 GROUP·VERSION 합쳐 apiVersion 재구성. 필드 뜻까지 보여 줘 YAML 쓸 때 가장 빠름
kubectl api-versions 이 클러스터가 지원하는 API 그룹 목록 여기 없는 그룹을 쓰면 no matches for kind 오류
kubectl create namespace shop shop 네임스페이스 생성 (명령형) YAML 없이 즉시. Git에 기록이 남지 않아 학습 이후엔 manifest 권장
kubectl apply -f 00-namespace.yaml 네임스페이스를 선언 파일로 생성 (선언형) 파일이 Git에 남아 재현 가능. 1일차 명령형/선언형 차이 그대로
kubectl apply -f shop-api.yaml manifest로 Pod 생성 spec: Forbidden ... 오류시 떠 있는 Pod 필드 수정 시도가 원인 — delete 후 apply
kubectl get pods -n shop shop 구역의 Pod 목록 -n 생략하면 default를 봐서 "Pod가 없다"고 착각하기 쉬움
kubectl get pods -A 모든 네임스페이스의 Pod 목록 어느 구역에 무엇이 떴는지 한눈에. 디버깅 첫 수
kubectl describe pod shop-api -n shop Pod의 상세 상태와 Events Events 아래부터 읽는 습관 — 1일차 4교시 그대로
kubectl delete pod shop-api -n shop Pod 삭제 파드는 되살아나지 않는다. 직접 만든 Pod는 자동 복원되지 않음. Deployment가 관리하면 컨트롤러가 새 Pod를 만든다
kubectl edit pod shop-api -n shop 떠 있는 Pod의 제한된 필드만 수정 바꿀 수 있는 건 image·labels 정도. 나머지는 Forbidden. 급할 때 쓰고 파일도 고치기
kubectl config set-context --current --namespace=shop 현재 컨텍스트의 기본 네임스페이스를 shop으로 편하지만 kubeconfig에만 저장돼 오적용 사고가 잦다. 실습은 -n shop 유지
