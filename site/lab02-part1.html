태스크 1 — VPC 생성 (약 10분)

노드 3대는 2a 서브넷 하나에만 두지만, 서브넷을 2c에도 하나 더 만드는 이유는 7일차 ALB가 서로 다른 AZ의 서브넷 2개 이상을 요구하기 때문이다. 누적 실습이므로 지금 미리 준비한다.

태그: cap-vpc에 Project=capstone, Owner=cap 추가. 이 태그는 채점·정리 스크립트가 리소스를 찾는 기준이라 이후 모든 리소스에 같은 태그를 붙인다.

서로 다른 AZ의 서브넷 2개가 표로 보이면 정상.

태스크 2 — 보안 그룹: 자기 참조 한 줄 (약 5분)

노드 사이에는 API 서버(6443), kubelet(10250), etcd, Calico VXLAN(UDP 4789) 등 여러 포트가 필요하다. 이 실습은 같은 보안 그룹끼리 모든 트래픽을 허용하는 자기 참조 규칙 하나로 처리하고, 인터넷에서 들어오는 규칙은 만들지 않는다.

cap-k8s-node-sg(VPC: cap-vpc)를 인바운드 규칙 없이 생성하고, 생성 뒤 인바운드 규칙 편집에서 유형 "모든 트래픽" · 소스 "cap-k8s-node-sg(자기 자신)"을 추가한다.

주의: 자기 참조 규칙은 보안 그룹이 만들어진 뒤에만 추가할 수 있다. 생성 화면에서는 아직 자기 자신을 소스로 고를 수 없기 때문이다.

프로토콜 -1(모든 트래픽), 소스가 자기 sg- ID, IP 범위 개수 0이면 정상.

보안: 인바운드에 0.0.0.0/0이 없으므로 인터넷에서 노드로 들어오는 연결은 모두 차단된다. Session Manager는 노드의 SSM 에이전트가 바깥으로 HTTPS 연결을 맺는 방식이라 인바운드 규칙이 필요 없다.

E

태스크 3 — IAM 역할 (약 5분)

EC2가 Systems Manager에 자신을 등록하려면 IAM 역할이 필요하다. 역할이 없으면 SSM 에이전트가 실행 중이어도 접속 수단이 없어진다(SSH도 안 쓰므로). 7일차에는 이 역할에 EBS CSI용 정책을 추가한다.

AWS 서비스 · EC2 사용 사례로 역할을 만들고 AmazonSSMManagedInstanceCore 정책을 붙인다. 이름 cap-k8s-node-role, 태그 Project=capstone · Owner=cap.

참고: 콘솔에서 EC2용 역할을 만들면 같은 이름의 인스턴스 프로파일이 자동 생성된다. EC2 시작 화면에서는 이 인스턴스 프로파일 이름을 선택한다.

두 줄(cap-k8s-node-role / AmazonSSMManagedInstanceCore)이 보이면 정상.

주의: kubeadm init은 vCPU 2개 미만이면 [ERROR NumCPU]로 중단된다.

경고 — 홉 제한 2는 7일차 EBS CSI 드라이버를 위한 설정이다. 드라이버는 Pod 안에서 인스턴스 메타데이터를 조회하는데, 홉 제한이 1이면 컨테이너 네트워크를 한 번 더 거치는 요청이 차단된다. 지금 설정하지 않으면 7일차에 원인을 찾기 어려운 실패를 겪는다.

참고: 키 페어는 인스턴스 시작 때만 지정할 수 있다. 대신 IAM 역할 지정을 빠뜨리면 접속 수단이 없어지니 주의하라.

유형 · AZ · IP · 프로파일 · 홉 제한 2가 모두 맞으면 정상. 시작 후 2~3분 뒤 aws ssm describe-instance-information에서 Online이면 접속 준비 끝.

태스크 5 — OS 기본 설정 (약 15분, 노드 셸)

이 태스크~태스크 8까지의 상태를 AMI로 복제해 워커를 만든다 — 모든 노드의 공통 기반이다.

접속 직후 sudo -i부터: Session Manager 세션은 ssm-user의 sh로 시작한다. sh에는 source나 프로세스 치환 같은 bash 문법이 없어 sh: 1: source: not found가 난다. root bash로 전환하면 사라진다. 문서의 노드 명령은 모두 sudo -i 상태를 전제한다.

169.254.169.123 앞에 ^*가 보이면 동기화된 것. etcd와 인증서 검증은 노드 간 시간 차이에 민감하다. 이 주소는 VPC 안에서 응답하는 링크 로컬이라 인터넷 경로와 무관하게 항상 도달한다.

스왑 확인: swapon --show가 아무것도 출력하지 않으면 정상. Ubuntu 클라우드 AMI는 스왑을 만들지 않아 swapoff가 필요 없다.

경고: preserve_hostname을 빠뜨리면 재부팅 후 호스트 이름이 ip-10-20-1-10으로 돌아간다. 쿠버네티스 노드 이름은 호스트 이름으로 정해지므로 노드가 NotReady가 되거나 중복 등록된다. 재접속 후 hostname이 cap-master를 출력하는지 확인한다.

태스크 6 — 커널 모듈과 네트워크 파라미터 (약 5분)

두 파라미터가 모두 = 1로 보이면 정상. br_netfilter는 브리지 트래픽도 iptables를 거치게 해 Pod 네트워크 정책이 동작하게 만들고, ip_forward는 노드가 다른 인터페이스 간 패킷을 전달하게 한다.

태스크 7 — containerd 2.x 설치 (약 15분)

주의: Ubuntu 24.04 기본 저장소의 containerd는 1.7.x다. Kubernetes v1.36에는 containerd 2.x를 쓰므로 Docker 공식 저장소의 containerd.io를 설치한다. 1.7.x용 설정 명령은 2.x에서 동작하지 않는다.

containerd/v2 2.x가 보이면 정상. 이어서 기본 설정 생성:

version = 3 또는 4면 2.x 형식 정상. 이 단계를 건너뛰면 안 된다 — 패키지 기본 설정에는 disabled_plugins = ["cri"]가 있어 쿠버네티스가 동작하지 않는다.

경고: SystemdCgroup이 두 줄이 되면 TOML 중복 키로 containerd가 시작되지 않는다. 그러면 기본 설정 생성 단계부터 다시 수행한다.

config OK · active · CRI 플러그인 줄이 모두 ok면 정상.

고려 사항: Docker Hub는 익명 이미지 다운로드를 공인 IP 기준으로 제한한다. 강의실 전체가 실습하면 한도에 걸리기 쉬워 미러를 먼저 조회하고, 실패하면 원본 레지스트리로 넘어가도록 구성한다. config_path 방식(certs.d)이 2.x 방식이고, 옛 registry.mirrors 방식은 쓰지 않는다.

태스크 8 — kubeadm·kubelet·kubectl v1.36 (약 10분)

주의: 세 패키지는 반드시 같은 버전이어야 한다. apt-mark hold를 빠뜨리면 apt upgrade 때 버전이 어긋날 수 있다.

참고: cri-tools는 컨테이너 런타임을 직접 들여다보는 crictl 명령을 제공한다. kubeadm과 함께 자동 설치되지 않으므로 따로 설치하고, AMI 생성 전에 설치하면 워커에도 그대로 포함된다. 이 시점에 kubelet은 설정이 없어 재시작을 반복하며 — kubeadm init 전까지는 정상이다.

두 줄의 pause 이미지 이름이 같으면 정상. (2일차 이론의 pause 컨테이너와 같은 이미지다.)

태스크 9 — AMI 생성과 워커 2대 (약 25분)

경고: AMI는 반드시 kubeadm init 전에 만든다. 초기화된 클러스터 상태(/etc/kubernetes, /var/lib/etcd)가 들어간 AMI로 워커를 만들면 인증서와 etcd 데이터가 복제되어 클러스터가 깨진다.

복제 전 정리 — machine-id와 SSM 등록 정보는 인스턴스마다 달라야 한다:

에이전트를 멈추는 순간 세션이 끊길 수 있다 — 명령은 이미 실행된 것이므로 그대로 다음으로 넘어간다. 비워 둔 machine-id는 다음 부팅 때 새로 만들어진다.

콘솔에서 cap-master → 이미지 생성: 이름 cap-k8s-base-1.36, 재부팅 체크 유지, 태그 Project=capstone · Owner=cap. AMI가 "사용 가능"이 될 때까지 5~10분 기다린다(이미지 생성 중 cap-master가 재부팅되며, SSM 에이전트는 자동 재시작된다).

AMI로 워커 2대를 시작한다 — cap-node1(기본 IP 10.20.1.11), cap-node2(10.20.1.12). 태스크 4와 같은 설정(유형·서브넷·보안 그룹·스토리지·프로파일·V2·홉 제한 2).

주의 — AMI에 들어가지 않는 인스턴스 속성: IAM 인스턴스 프로파일, 메타데이터 홉 제한, 태그(AMI에 붙인 Project·Owner도 복사되지 않음). 워커를 시작할 때 세 가지 모두 반드시 다시 지정한다.

워커 호스트 이름 — 각 워커에 접속해:

첫 hostname은 cap-master로 나온다(AMI에 복제된 값). 이 단계를 잊으면 워커 두 대의 이름이 모두 cap-master가 되어 kubeadm join이 실패하거나 노드가 서로 덮어쓴다. 세션에 들어가면 항상 hostname부터 확인하라.

0% packet loss면 보안 그룹 자기 참조 규칙이 동작하는 것이다.
